# Project Persistence and Navigation Plan

## Decision

Projects will be stored as versioned JSON files in the app's private internal storage:

```text
filesDir/projects/{projectId}.json
```

This app is an individual tool and is unlikely to contain thousands of projects. A file-per-project snapshot is therefore simpler and more portable than introducing a database.

Room remains a possible future option if the product later needs cloud sync, object-level search, collaboration, project history, or very large project collections.

## Project contents

Each JSON file represents the complete editable project snapshot:

- stable project UUID;
- project name;
- created and updated timestamps;
- `schemaVersion`;
- selected location and location label;
- map camera state: center, zoom, bearing, and pitch;
- geographic map boundary;
- manually drawn buildings, walls, and trees;
- loaded building geometry and heights;
- loaded-building identity metadata;
- loaded-building height overrides;
- suppressed or deleted loaded buildings;
- selected date/time if analysis time is considered part of the project.

Derived values such as visible buildings and calculated shadows should not be persisted. They should be recalculated after loading.

## Boundary representation

The map boundary must be stored as geographic coordinates, not screen pixels. Capture the current viewport corners from the Mapbox map and save them as a polygon. Save the camera state separately so the project can restore both:

- the geographic area represented by the project; and
- the user's last viewing position.

## Repository design

Keep file access behind a repository so UI and ViewModels do not depend directly on `File` or JSON APIs:

```text
ProjectRepository
├── listProjects()
├── loadProject(id)
├── saveProject(project)
├── renameProject(id, name)
├── duplicateProject(id)
└── deleteProject(id)
```

The project list can be generated by scanning the projects directory and reading lightweight metadata from each file. If this becomes slow, add a small `projects-index.json`; do not introduce Room prematurely.

Writes should be atomic: write to a temporary file, flush it, then replace the previous project file. A failed save must not corrupt the last valid project.

## JSON model and migrations

Use persistence DTOs separate from domain/UI models. Keep the JSON format explicitly versioned:

```json
{
  "schemaVersion": 1,
  "id": "project-uuid",
  "name": "My project",
  "createdAt": 1763300000000,
  "updatedAt": 1763300100000,
  "camera": {},
  "boundary": [],
  "drawnBuildings": [],
  "drawnWalls": [],
  "drawnTrees": [],
  "loadedBuildings": [],
  "loadedBuildingOverrides": [],
  "suppressedLoadedBuildings": []
}
```

On load:

1. Parse the JSON.
2. Check `schemaVersion`.
3. Migrate older versions in memory when supported.
4. Map DTOs into domain models.
5. Recalculate automatic overlaps and shadows.
6. Restore the map camera.

Malformed files should produce a recoverable error in the project list rather than crash the app.

## Save behavior

For a new project:

1. User taps `Save project`.
2. App asks for a project name.
3. App captures the current map boundary and camera state.
4. App serializes the complete scene snapshot.
5. App writes `{projectId}.json`.
6. The new project becomes active.

For an existing project, `Save project` updates the same file. `Save as...` creates a new UUID and leaves the original project unchanged.

Track an `isDirty` state when drawings, loaded-object edits, suppressions, boundary, camera, or saved analysis time change. Opening another project, creating a new project, or leaving the map while dirty should request confirmation.

Loaded buildings should be restored from the saved snapshot by default. Refreshing Mapbox building data should be an explicit future action so reopening a project does not unexpectedly change user edits.

## Navigation flow

Extend the existing Navigation 3 back stack:

```text
Map
├── Projects
│   ├── Save Project dialog
│   ├── Rename Project dialog
│   └── Delete Project dialog
├── Settings
└── Location Search
```

The project list is a full-screen destination. Selecting a project loads it and returns to the map. Drawing modes, property sheets, confirmation dialogs, and 3D mode remain local map UI state unless they later require independent back-stack behavior.

## Implementation phases

### Phase 1: JSON persistence foundation

- Add JSON serialization dependency or use the project's selected serialization approach.
- Define project DTOs and `ProjectSnapshot`.
- Implement `ProjectRepository` using `filesDir/projects`.
- Add atomic writes and schema-version validation.
- Add round-trip, malformed-file, and migration tests.

### Phase 2: Capture and restore map state

- Persist viewport boundary polygon.
- Persist camera center, zoom, bearing, and pitch.
- Restore camera state when opening a project.
- Persist selected location and analysis time.

### Phase 3: Save and load the scene

- Serialize manual buildings, walls, and trees.
- Serialize loaded buildings and identity metadata.
- Serialize overrides and suppressions.
- Add active-project and dirty-state handling to the ViewModel.
- Add save and save-as flows.

### Phase 4: Project list and navigation

- Add `ProjectsDestination` to `AppNavigation`.
- Add loading, empty, populated, and error states.
- Add open, rename, duplicate, and delete actions.
- Add unsaved-changes confirmation.

### Phase 5: Import and export

- Add `ACTION_CREATE_DOCUMENT` export.
- Add `ACTION_OPEN_DOCUMENT` import.
- Validate imported schema versions.
- Handle duplicate project IDs safely.

## Acceptance criteria

- A user can save a named project as a JSON file.
- Manual and loaded scene objects survive closing and reopening the app.
- Loaded-object overrides and suppressions survive reload.
- The map boundary and camera restore correctly.
- A project opens without network access.
- The project list survives app restarts.
- Existing projects update in place when saved.
- Save-as creates an independent copy.
- Unsaved changes cannot be lost accidentally.
- Invalid or unsupported JSON files show a recoverable error.
